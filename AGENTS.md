# Instructions for AI Agents

## Repository scope

This repository contains only the backend for UFVJM's undergraduate thesis management system. The frontend is maintained in a separate React project. Implement the API, business rules, persistence, authentication, and backend integrations here; do not create React components or pages in this repository. Keep API contracts clear for the frontend.

Before changing code, read the settings and modules related to the task. Respect the existing structure and make small changes that fit the project's current stage. Do not assume that requirements described in the assignment have already been implemented. When a change depends on external services or architectural decisions that are not yet configured, document the configuration requirements and keep component boundaries clear.

## System requirements

- Use Django, Django REST Framework, Python, and PostgreSQL. Read credentials, keys, and other secrets from environment variables loaded through `.env`; never put them in code, logs, or versioned files. Keep `.env` ignored by Git. Update `.env.example` with variable names and fictitious values only.
- Use `django-allauth` for system authentication, following the existing dependencies and configuration.
- Model and enforce permissions for administrators, course coordinators, professors/advisors, students, and external thesis committee members. Temporary access for external members must use tokens with limited lifetime and scope, without requiring a permanent account.
- Restrict administrative and submission operations to authenticated and authorized users. The academic assignment requires the admin area to be restricted to the institutional network via IP/VPN; implement this only with trusted environment configuration and never trust client-supplied IP headers.
- Allow anonymous access to the public repository only for published theses.
- The domain includes students, professors, courses, theses, committees, evaluations, and supplementary documents. Preserve relationships and business rules in the backend, even though the UI is in another repository.
- Theses must support drafts, submission, status tracking, and search by title, author/student, advisor, course, defense year, and keywords. CRUD and filters must enforce permissions and state rules.
- Allow a defense committee to be scheduled only after advisor approval. Validate member availability and time conflicts. Each member records their evaluation; calculate the final result only after all required evaluations have been submitted.
- Publish a thesis to the public repository only after final committee approval, submission of a corrected version when applicable, and recording of a signed publication authorization form. Never allow a published thesis to be deleted through ordinary CRUD operations.
- On upload, accept PDF files only, enforce a configurable size limit (50 MB is the assignment's reference), and calculate SHA-256 for integrity and deduplication. Recheck integrity in workflows where approval or publication depends on the file.
- Process text extraction, indexing, notifications, and other long-running tasks asynchronously through an event queue, never inside the HTTP request. Expected events include submission, scheduling, evaluation recorded, and publication.
- Redis is a stated requirement for session and search caching, in-progress upload tracking, and rate limiting. Use predictable namespaced keys with appropriate expiration; do not store secrets or unnecessary personal data in the cache.
- The assignment proposes RabbitMQ or Kafka for queues and an architecture with authentication, thesis, committee, repository/search, notifications, and reporting services. Preserve these functional boundaries and decoupled APIs. Do not create infrastructure or microservices unless the concrete task requires them; avoid duplicating responsibilities or introducing unavailable dependencies.
- The REST API must return JSON. Expected public resources include published theses with search/filters, courses, and advisors. CRUD for students, theses, committees, and evaluations requires authentication and authorization. Keep names, formats, HTTP status codes, and pagination consistent.
- The system should support dashboards/reports for theses by course, advisor, and defense year, approval rate, and average time between submission and defense. These are calculated on the backend by `GET /api/v1/reports/overview` and exported as PDF by `GET /api/v1/reports/overview/pdf` (see "Reports endpoint").
- The expected development and deployment environment is Linux.

## Implementation practices

### Python and readability

- Use type hints for new or changed functions and methods, including parameters and return values. Prefer precise types and explicit structures; avoid `Any` when a concrete type is possible.
- Add type hints for local variables when the type is not obvious or to improve clarity.
- Keep function and method parameter declarations on a single line whenever practical. Never break function/method/constructor parameter declarations across multiple lines. If a declaration becomes excessively long, group related parameters into a small object and pass that object instead of breaking parameter lists across multiple lines. Line breaks are allowed in function/method/constructor calls only when there are many arguments.
- Do not chain multiple function calls on the same line or split a single function call across multiple lines unnecessarily. Avoid patterns like `func1(func2(x))` in a single complex statement when clarity suffers, and do not break calls like `parse_datetime(str(x))` across lines. Cache intermediate results in clearly named variables on separate lines.
- Do not chain method calls across multiple lines (e.g., avoid breaking `.filter(...).first()` across lines). Keep method chains on a single line when possible, or assign intermediate objects to variables.
- Write all docstrings in English and follow the Google style (`Args`, `Returns`, `Raises`, and `Examples` where applicable). Document purpose, non-obvious behavior, side effects, and relevant exceptions; do not merely repeat the signature. Docstrings must follow this exact format: opening triple quotes on its own line, documentation on the next line with indentation matching the triple quotes, closing triple quotes on its own line at the same indentation level as opening. Do NOT add blank lines between triple quotes and documentation.
- Write developer-facing documentation and code comments in Portuguese. Add comments only to explain why a particular approach was chosen or to clarify something that is not obvious from the code. The code itself should make clear what it does; do not add comments that merely narrate operations.
- Logging messages may be written in English to keep them consistent across the codebase.
- Use descriptive and consistent names: `PascalCase` for classes, `snake_case` for functions, methods, variables, and modules, and `UPPER_SNAKE_CASE` for constants. In Django, choose clear names for models, fields, serializers, views, permissions, services, and URLs; avoid obscure abbreviations and generic names such as `data`, `obj`, or `helper` when a specific name is practical.
- Prefer small functions, single responsibilities, and explicit business rules. Avoid duplication, mutable global state, domain logic hidden in views/serializers, and abstractions without a concrete use.
- Use `Decimal` for grades or other values that require decimal precision when appropriate. Use timezone-aware dates and keep `USE_TZ` enabled.

### Directory endpoints (permissions and shapes)

- `GET /api/v1/public/advisors` is the only anonymous directory endpoint. It returns active advisors only, searches by name only (never e-mail — the public side of the directory must not leak addresses), exposes only `id`, `name` and `avatarUrl`, is paginated (`count`, `page`, `pageSize`, `totalPages`, `lastPageCount`), and is cached for 60 s. Requires no authentication; search by name is case-insensitive.
- `GET /api/v1/users` returns the student/coordinator/administrator directory and requires the COORDINATOR or ADMIN role (or staff/superuser); students and advisors receive 403. The e-mail and the caller-relevant `roles` are included because the full directory is internal; paginate with `page`/`pageSize` (default 20, max 50), cache for 60 s, and pass `role=` to filter (`STUDENT`, `ADVISOR`, `COORDINATOR`, `ADMIN`); any other value returns 400.
- `GET /api/v1/users/suggest` backs the pickers. Advisors see only other advisors (matching the public advisors list); coordinators and administrators see the full directory, narrowable with `role=` (validated); students receive 403. Up to three results, name or e-mail prefix, capped `USER_SUGGEST_*` constants, cached briefly (45 s) keyed by role set + query; scope `user_suggest` (60/min); do not expose it anonymously nor broaden the advisor scope to other roles without an explicit, documented decision.
- Whichever endpoint you add or change: expose only `id`, `name`, `email`, `avatarUrl` (and role information where callers are authorized to read it), `select_related`/`prefetch_related` avatars, `.only(...)`, deduplicate with `distinct()`, cache identical queries for a minute, and return the standard pagination envelope.

### Reports endpoint

- `GET /api/v1/reports/overview` lives in the `reports` app (no models; services in `reports/services.py`). It returns `scope` (`ALL` or `COORDINATED_COURSES`), `filters`, `summary`, `byCourse`, `byAdvisor`, `byDefenseYear` and `options` (`courses`, `advisors`, `years`), all in camelCase. Filters: `courseId`, `advisorId`, `year` (defense year in America/Sao_Paulo) and `scope=coordinated`; invalid values return 400.
- Permissions: ADMIN (or superuser) sees every course; COORDINATOR sees only the courses linked by `coordinated_courses_filter` (`theses/services.py`: `coordinator` FK, `coordinator_email`, active `UserCourseAssignment`). An administrator may pass `scope=coordinated` to see only their own courses. Advisors, students and external sessions receive 403. A coordinator's report never includes theses they advise in other courses.
- Definitions: theses are non-deleted and non-draft; approval rate is per completed defense, (approved + approved with remarks) / defenses with a recorded result, `null` without data; average time is from the last `SUBMITTED` status-history entry before the defense to `scheduled_datetime`, in days with one decimal. With `year`, theses are those with a completed defense in that year.
- `Defense` has no `result` column: the result is read from `ThesisStatusHistory.metadata` (`defenseId`/`defenseResult`) written by `_finalize_defense`. Keep those keys in sync with `reports/services.py`; `reports/tests` exercises the real close path and fails if they drift.
- Aggregate in the database (`values().annotate(Count/Avg)`), never by iterating rows in Python; the query count must not grow with data (covered by a test). Cache for 60 s under `reports:overview:<all|user:id>:<filters>` through `get_overview_payload`; throttle scope `reports` (60/min).
- `GET /api/v1/reports/overview/pdf` exports the same report as an A4 PDF in Portuguese (`reports/pdf.py`, ReportLab, no system packages). It reuses the filters serializer, the permissions, `resolve_report_scope` and the cached payload from `get_overview_payload`; the renderer only formats that payload and never queries or recomputes. Contents: title, generation time (America/Sao_Paulo), scope and filters by name (from `options`; a course outside the caller's scope is described, not named), summary with "Taxa de aprovação em bancas", and tables by course, advisor and defense year. Response: `application/pdf`, `Content-Disposition: attachment; filename="relatorio-tcc-AAAAMMDD-HHMM.pdf"`, `Cache-Control: no-store`; errors (400/401/403/429) are always JSON, even with `Accept: application/pdf`. Its own throttle scope `reports_export` (10/min) so exports do not consume the dashboard quota. Every export is recorded in `audit_log` as `DOWNLOAD` (`entity_type="ReportOverview"`, `entity_id="overview"`), with metadata limited to `format`, `scope`, `courseId`, `advisorId` and `year` (identifiers only, no names). `CORS_EXPOSE_HEADERS` includes `Content-Disposition` so the frontend can read the file name.

### Public repository

- Search, filters and payloads live in `theses/repository.py`; cache in `theses/repository_cache.py`; legacy import, published edits, unpublication and deletion in `theses/repository_management.py`. Anonymous endpoints (`/api/v1/public/theses`, `/filters`, `/<id>`, `/<id>/download`, `/api/v1/public/courses`) run without authentication, throttle scopes `public_repository`/`public_download`, and never expose e-mails.
- Only `PUBLISHED` + `is_public` + non-deleted theses are public. The year filter is the defense year (`defense_year`, filled on publication), never a fixed range.
- Search pages are cached under `busca:<sha256>`; every change to published data must call `invalidate_public_repository_cache()` (rotates the version token, no prefix deletes).
- Publication is automatic through `publish_if_ready` (final approval + corrected version when approved with remarks + validated authorization); new steps that can complete those conditions must call it. It must never make the calling step fail.
- Published (or once published) theses cannot be deleted by any path (model, queryset, cascade, admin); use `unpublish_thesis` (reason required, `ARCHIVED`). Repository management is limited to administrators and coordinators of the course (`user_manages_course`).

### Asynchronous events (transactional outbox + RabbitMQ)

- Apps: `events` (outbox, broker, publisher, topology) and `notifications` (templates, deliveries, consumer). Client library: `pika` (blocking connection, publisher confirms). No Celery.
- Producers never talk to the broker. A state transition records its event with `events.outbox.record_event` inside the same `transaction.atomic` as the change (it raises `RuntimeError` outside an atomic block), through the helpers in `theses/events.py`. Emitted today: `thesis.submitted`, `defense.scheduled`, `defense.evaluation_recorded`, `defense.completed` (manual and automatic close, inside the close savepoint), `thesis.defense_result_recorded` (manual result without a `Defense`), `thesis.published` and `defense.external_member_invited` (external member added, invitation resent or regenerated; payload `defenseId`, `thesisId`, `memberId`, `invitationId`, `trigger` = `CREATED`/`RESENT`/`REGENERATED`). The defense result is still computed synchronously in `_finalize_defense`.
- Contract: `events/catalog.py` is the single source of truth (`EventType`, version `"1.0"`, exact payload keys). Payloads carry only identifiers and codes (flat JSON scalars); never names, e-mails, notes, scores, decisions before the close, locations/meeting links or tokens. Consumers load everything else from the database. A new event needs: catalog entry, helper in the producing app, a planner and a seeded template in `notifications`, and tests. A breaking payload change requires a new version, never an in-place edit.
- Publisher (`publish_outbox_events`): batches with `SELECT ... FOR UPDATE SKIP LOCKED`, persistent messages with `mandatory=True` to the topic exchange `thesis.events` (routing key = event type). A message failure counts an attempt with exponential backoff (`next_attempt_at`, `OUTBOX_RETRY_*`) up to `max_attempts`, then `FAILED`; a broker outage (`BrokerUnavailableError`) stops the batch without counting attempts. Every broker connection error must be caught through `events.rabbitmq.BROKER_CONNECTION_ERRORS` (pika lets `socket.gaierror`/`OSError` escape when the host does not resolve). The idle loop calls `broker.keep_alive()` so heartbeats are serviced; a blocking pika connection that is not polled is closed by RabbitMQ after missed heartbeats.
- Topology (`events/topology.py`, command `declare_event_topology`): exchange, dead-letter exchange `thesis.events.dlx`, queue `notifications.thesis-events` (bindings `thesis.*`, `defense.*`) and its DLQ. Queue arguments cannot change on an existing queue. In Docker Compose the one-shot `init` service runs `migrate` and then `declare_event_topology`; `backend`, `event-publisher` and `notification-consumer` start only after it completes.
- Consumer (`consume_notifications`): idempotent through `processed_event` (composite key `consumer_group` + `event_id`); the marker and the `notification` rows are committed together and e-mails are sent only after the commit, one message per recipient. Ack on processed/duplicate; nack without requeue (DLQ) on undecodable, unknown type/version, payload outside the catalog or unexpected error; nack with requeue after a pause only when the database is unavailable. Delivery failures stay `FAILED` on the row; resending is manual (`consume_notifications --retry-pending`), as is requeueing failed outbox events (`publish_outbox_events --requeue-failed <id|all>`).
- Recipients: submission → advisor; defense scheduled → authors and advisor; evaluation recorded → advisor (progress only); defense completed → authors, advisor and evaluating members (alternates cannot evaluate and are not notified); manual result and publication → authors and advisor; external member invited → that external member only. Coordinators are not notified. Do not widen recipients or payloads without an explicit decision.
- External member token (`notifications/invitations.py`): the readable token exists only in the e-mail. Producers never create it: `theses.events.record_external_member_invited` records the event, replaces `token_hash` with an unmatchable digest (the previous token stops working at once) and sets `ExternalInvitation.token_event_id` to the new event. The consumer locks the invitation and issues a token only when `token_event_id` matches the event (older, redelivered or out-of-order events issue nothing), the invitation is usable and the defense is `SCHEDULED`/`IN_PROGRESS`; it stores only the hash, keeps a masked copy (`UFVJM-****`) in `notification`, sends the real token only in the outgoing message, then sets `token_sent_at` and audits `INVITE` (`INVITATION_EMAIL_SENT`/`INVITATION_EMAIL_RESENT`, identifiers only, system actor). `--retry-pending` never resends the stored body of this template: it issues a new token, commits the hash and then sends; superseded or invalid invitations become `CANCELLED`. Delivery errors are scrubbed of e-mail addresses and token-like values. Tests prove the token is absent from the outbox, published envelopes, `notification`, `audit_log` and every log record (`notifications/tests/token_leaks.py`); never weaken them.
- E-mail backend: never `console.EmailBackend` (it prints messages, and tokens, to the logs; system check `notifications.W001`). Docker Compose sends to Mailpit (UI on `127.0.0.1:8025`, SMTP not published); production configures its SMTP separately.
- Logging: event/notification identifiers, types and outcomes only. Never log payloads, e-mail addresses, the broker URL, or exception messages from the broker, SMTP or database (log the exception class), since they may contain hosts, users or row values.
- Tests never need a running RabbitMQ: use `events.tests.fakes.InMemoryEventBroker`, call `handle_event` directly, mock `pika.BlockingConnection`, and assert e-mails with `django.core.mail.outbox`. A manual smoke test against the real broker is described in the README.

### Django and API

- Centralize domain validation so it applies to every write path, not only the UI or a single endpoint.
- Use serializers to validate and transform API data, DRF permissions for authorization, and services or domain methods for multi-step workflows. Do not trust user, role, status, or authorship fields submitted by the client without validation.
- Keep queries efficient: use `select_related`/`prefetch_related` where appropriate, filter in the database, and paginate potentially large lists.
- Create and version migrations alongside model changes. Do not edit migrations that have already been applied as if they were disposable, and do not change existing data without a deliberate migration.
- Do not expose stack traces, private data, local paths, or internal implementation details in HTTP responses. Use consistent status codes and error messages.
- Secure uploads and downloads: validate content and size, generate safe storage names, do not trust client-provided filenames or MIME types, and enforce permissions when accessing files.

### Logging: severity and detail

- Use the Python standard library's `logging` module and obtain a logger per module (`logging.getLogger(__name__)`). Do not use `print` for application diagnostics.
- Choose severity based on the event's importance and impact: `DEBUG` for internal diagnostics; `INFO` for relevant normal events; `WARNING` for unexpected but recoverable conditions; `ERROR` for an operation failure; `CRITICAL` for a failure that threatens service continuity. Do not raise severity merely to get more output.
- Control detail separately from severity: include useful, concise context in log messages (for example, entity identifier, step, and outcome), and let handler configuration determine the level and format for each environment. Never log tokens, passwords, keys, connection URLs, document contents, unnecessary personal data, or complete payloads.
- Log exceptions with `logger.exception(...)` inside an exception handler when a traceback is useful. Do not catch broad exceptions to hide failures; handle only exceptions that can be resolved or meaningfully contextualized.
- For asynchronous workflows, log the event/task identifier and processing outcome without sensitive data. Avoid duplicate logs in layers that only propagate the same exception.

### Security and configuration

- Keep `SECRET_KEY`, PostgreSQL, Redis, broker, email, and integration credentials in environment variables. Document variable names and fictitious examples in `.env.example`.
- Apply least privilege to permissions, tokens, service credentials, and file access. Temporary tokens must expire and allow only their intended actions.
- Avoid raw SQL; if it is necessary, use bound parameters. Never build queries by interpolating user input.
- Consider privacy and auditing: record who performed relevant actions and when, without copying sensitive content into logs. Protect and retain audit records according to project configuration.

## Authentication (implemented rules)

- Use Django custom user `accounts.User` with UUID PK, `AbstractBaseUser + PermissionsMixin`, `email` unique, `name`, `is_staff`, `is_active`, `date_joined`, `is_superuser`; `USERNAME_FIELD="email"`, `REQUIRED_FIELDS=["name"]`. No `username`, `first_name`, `last_name`. Table `users_user`.
- Business roles stored in `user_profile_role` with history (no deletion on revoke, `revoked_at`). Only one active role per (user, role). The effective role is always derived from the database, following the priority `ADMIN > COORDINATOR > ADVISOR > STUDENT`; there is no client-side profile switching or session-selected role.
- Login only via Google Workspace institutional accounts (`@ufvjm.edu.br`). Use django-allauth in headless/social mode (`SOCIALACCOUNT_ONLY=True`). Validate domain, `email_verified` and `hd`. Provision user on first login and assign default `STUDENT` role. No local signup/password recovery.
- API façade versioned `/api/v1`. `GET /api/v1/session` returns `authenticated`, `authType`, `user` (including `avatarUrl` from the Google profile when available), `role`, `profile`, `roles`, `permissions`, `csrfToken`, `externalInvitation` (200 for anonymous). `DELETE /api/v1/session` logs out and clears the session cookie. `GET /api/v1/auth/google/start?next=` returns `{url}` to start Google auth. The session `role` is read-only and comes from the user's roles in the database.
- External committee members use temporary invitations (`external_invitation`): human token `UFVJM-XXXX-XXXX-XXXX-XXXX` (base32-like), only its `SHA-256` stored in `token_hash` (`BinaryField(max_length=32)`). Invitations are created only by `POST /api/v1/defenses/<id>/members/external`; the token is generated by the notification consumer and sent only by e-mail, never returned by the API (see "Asynchronous events"). `POST .../members/<memberId>/resend-invitation` (manages the defense; invitation still `PENDING`/`ACCEPTED`, not expired nor revoked; expiration not extended) and `POST .../members/<memberId>/regenerate-token` (new invitation, for used, expired or revoked ones; keeps availability and evaluation; audited as `EXTERNAL_TOKEN_REGENERATED`) both answer 202 with `Cache-Control: no-store` and share the throttle scope `invitation_resend` (5/min). Invitation audit events (`INVITATION_EMAIL_SENT`, `INVITATION_EMAIL_RESENT`, `INVITATION_RESEND_REQUESTED`) use the typed `InvitationDeliveryPayload` in `accounts/audit_events.py`. `POST /api/v1/auth/external-token` exchanges token for session (single use: the invitation becomes `USED`), flushes previous session, rotates keys, sets `external_invitation_id`/expiration. Sessions authenticated via `ExternalInvitationSessionAuthentication` (no permanent User). TTL configurable.
- Sessions use `SESSION_ENGINE="django.contrib.sessions.backends.cached_db"` with Redis cache. Cookies HttpOnly, CSRF handled. CORS/CSRF configured for frontend.
- Audit: `session_audit` tracks sessions (IP, user agent, origin INSTITUTIONAL_NETWORK/VPN/EXTERNAL, login/logout/activity). `audit_log` is append-only with SHA-256 hash chain (`previous_hash`, `row_hash`). Actions include LOGIN, LOGOUT, LOGIN_FAILED, TOKEN_ACCESS, etc.
- Administrative areas (`/admin/`, `/api/v1/admin/`) restricted by IP/VPN via `ADMIN_ALLOWED_CIDRS`; never trust `X-Forwarded-For` without `TRUSTED_PROXY_COUNT>0`. Empty list denies all in production; return 404 on denial. DEBUG allows localhost.
- Users: soft delete only (`is_active=False`, revoke roles). Protect last active admin. Email immutable after creation. Admin endpoints: `GET/POST/PATCH/DELETE /api/v1/admin/users`, `GET /api/v1/admin/audit-logs`, `GET /api/v1/admin/external-invitations` (list, no token) and `DELETE /api/v1/admin/external-invitations/<id>` (revoke); there is no standalone invitation creation.
- Allauth headless configured with browser client; frontend sends `credentials: 'include'`, reads `csrftoken`, sends `X-CSRFToken`.
